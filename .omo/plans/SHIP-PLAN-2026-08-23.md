gate: sandboxing ships default-on for audio and MIDI, and no verdict or deliverable depends on CV
reaching a sandboxed plugin. Option B (build it) is costed in §6.

### F11 — The sandbox helper is never installed into plugin bundles. With sandboxing default-on, P4.4 fails by construction.

This is a **build/install defect to fix**, not a pre-flight check. The defect is narrower than
revision 2 claimed — it is a **CMake gap only**; the signing script already handles the case.

1. **Resolution code exists and is correct.** `src/engine/sandboxhost.hpp:1162` resolves the helper
   in order: env override → `<bundle>/Contents/Helpers` → executable-adjacent → honest failure.
   Covered by `SandboxHelperDiscoveryTests` (`test/CMakeLists.txt:360`).
2. **No CMake rule ever copies the helper into a plugin bundle — this is the whole defect.** The
   only nesting rule is `CMakeLists.txt:191-197`, a `POST_BUILD` custom command copying
   `element_sandbox_host` into `$<TARGET_BUNDLE_DIR:element_app>/Contents/Helpers/Element Sandbox
   Host.app` — that is **Element.app, the standalone app, only**. No equivalent exists for
   `element_instrument`, `element_effect`, or `element_midi_effect`.
3. **The signing sweep already covers it — revision 2's claim that it would not is RETRACTED.**
   `scripts/sign-all-macos.sh:53-58` runs a second find:
   `find "$BUILD_DIR" -name "Element Sandbox Host.app" -type d ! -path "*/Element.app/*"`.
   A helper at `…/KV-Element.component/Contents/Helpers/Element Sandbox Host.app` contains **no
   `/Element.app/` path segment** (the segment is `KV-Element.component`), so the exclusion does not
   fire and the helper **is** matched and signed. Ordering is also already correct: Step 1 signs all
   helpers (`:47` and `:53-58`) **before** Step 2 signs plugin bundles (`:67-83`), preserving the
   innermost-first seal. Note the helper is signed with `cmake/entitlements-sandbox.plist`
   (least-privilege: JIT + `disable-library-validation`, deliberately **no** `device.audio-input` —
   the worker uses shared memory), not the app's `cmake/entitlements.plist`.

Because `pluginSandboxMode=1` ships **default-on** (F7's `7e6f4bbd`), an Element plugin instance
loading a third-party plugin inside a DAW will look for a helper that was never installed and is not
executable-adjacent in that layout. **P4.4 fails by construction until the CMake rules are added.**
The fix belongs in the serial phase, before any lane opens — see P1.5b.

**Installer-path corollary (verified).** The gap repeats one layer down in packaging.
`installer/build_pkg.sh:69-96` bundles the helper into
`$PKG_ROOT/Applications/Element.app/Contents/Helpers` **only** — no plugin bundle gets one. Two
further consequences: (a) the whole signing block at `:391` is gated on
`[ -n "${DEVELOPER_ID_APP:-}" ]`, which is **unset on our ad-hoc path**, so `build_pkg.sh` signs
nothing and the shipped signatures come entirely from a prior `sign-all-macos.sh` run; and (b)
`:86-90` does `rm -rf "$HELPER_DEST/$HELPER_NAME"` followed by `cp -R` **into the already-copied,
already-signed `Element.app` staged in `PKG_ROOT`** — mutating a sealed bundle after signing, which
can invalidate exactly the seal P5.3 checks with `codesign --verify --deep --strict`. Both are
addressed in P1.5b and P5.

## 1. Principles

1. **Evidence before action, especially where the action is irreversible.** Every destructive git
   operation is preceded by a read-only probe and a verifiable backup. Revision 1 asserted three
   things (origin unreachable, filter-repo deleted the refs, credentials possibly public) that
   measurement then falsified — a standing reminder that plausible causal stories are not evidence.
2. **A disabled test is a hypothesis about who is wrong, not a verdict.** The quarantine comments
   blame the tests, but they are self-declared and marked `unverified`. Assumptions are checked
   against the implementation *before* any test is rewritten.
3. **Ship the truth, not the docs.** Where a doc and the code disagree, the code wins and the doc is
   corrected in the same pass. Stale canonical docs already caused one wasted re-implementation
   (`2654b74b`).
4. **Serialise what touches `.git` or the build graph; parallelise only genuinely independent work.**
   Revision 1 parallelised a lane whose acceptance criterion depended on another lane's commits.
   Shared-substrate work is now serial by default.
5. **Real-time safety is non-negotiable.** No allocations or locks on the audio thread; atomic
   pointer swaps only. `AudioThreadAllocationTests` and `GraphNodeRenderSafetyTests` stay green
   across every engine change.

## 2. Decision Drivers (top 3)

1. **Irreversibility of the repo close-out.** The force-push and `--prune=now` cannot be undone from
   inside the repo. Backups exist and predate the filter-repo run, and F1 now scopes the push
   exactly (four heads, zero unknowns), so it can be done early and confidently — with the added
   obligation of disposing of three open PRs.
2. **Test-debt size collapsed, but its *shape* is still unproven.** F3 reduces 28 unknowns to four
   mechanical classes plus one feature build. What remains genuinely unknown is whether the
   "test-side error" label holds — and two specific suites can settle that cheaply. That makes a
   small discriminating experiment worth more than a committed lane plan.
3. **Manual DAW verification is the true critical path, and F11 currently guarantees it fails.**
   Nothing downstream is meaningful until the helper-install defect is fixed, which is why it moves
   into the serial phase ahead of all lane work.

## 3. Viable Options

### Option A — Full-bar sequential *(the spec read literally)*

Repo close-out → all test debt including CV transport → all UI gaps → plugin build → verify →
package → docs.

**Pros:** simplest to track; one thing in flight; no cross-lane invalidation.
**Cons:** reaches the never-configured plugin build and the F11 defect last, at the worst moment.
Buries an RT-critical engine feature (F4) inside a phase labelled "test debt". Longest wall-clock.

### Option B — Three-lane parallel, CV descoped *(revision 1's recommendation; retained as alternative)*

P0 → P1 → three parallel lanes (T: tests · U: UI · P: plugin build) → P3 gate → P4 → P5 → P6.

**Pros:** exercises the risky plugin build early; lanes touch mostly disjoint file sets.
**Cons — the architect's decisive objection:** Lane P's acceptance criterion "`webview/dist` newer
than `webview/src`" is **falsified by every Lane U commit**, because Lane U edits `webview/src` while
Lane P builds against a moving branch. The lane is either pinned to a fixed commit (and then verifies
something that is not what ships) or unpinned (and then its gate is meaningless). Revision 1 did not
resolve this. Option B remains viable **only** if Lane P is explicitly pinned to a fixed commit and
re-verified at P3.

### Option B-prime — Serial de-risking, then evidence-shaped lanes ★ **recommended**

P0 → P1 (repo close-out) → **P1.5b** (plugin configure probe + F11 helper-install fix, serial, S) →
**P2a** (discriminating experiment: T1 plus T4's two R4 suspects) → **RE-DECISION POINT with
evidence** → remaining work shaped by what P2a found → P3 gate → P4 → P5 → P6.

**Pros:** resolves both live unknowns before committing to a shape. The plugin configure probe and
the F11 fix are small, serial, and unblock the critical path without needing a parallel lane at all
— which dissolves Option B's `dist`-freshness contradiction entirely. The two R4 suspects
(`RingBufferTests` capacity 256-vs-255, `RerouteNodeTests` MIDI ports 0-vs-1) are the cheapest
available test of whether the "test-side error" label is trustworthy: if both are genuinely bad
tests, the remaining 13 class-C suites are safe mechanical work; if either is a real engine bug, the
lane is an engine-debugging effort and must be resourced and sequenced differently.
**Cons:** inserts an explicit decision point, so the total shape is not knowable up front — which is
the honest position, but harder to put on a calendar. Slightly more serial work before parallelism
begins.

### Option C — Ship-gate-minimal

Repo close-out + `SandboxRealProcessTests` + F11 fix + plugin build/verify/package + docs. Defer the
28 suites and UI gaps.

**Pros:** fastest route to a signed, installable DMG with verified AU and VST3.
**Cons:** overrules Glen's locked answers to interview questions 6 and 7. Recorded for completeness;
**not recommended without Glen re-opening those answers.**

**Recommendation: Option B-prime.**

### P2a — Discriminating experiment *(serial, S)*

Two questions, answered with evidence, before any lane shape is committed.

**T1 — Root-cause `SandboxRealProcessTests/RealProcessRoundTrip`**

The assertion is `BOOST_CHECK_GE(successfulCycles, requiredSuccesses)` —
`test/engine/SandboxRealProcessTest.cpp:141` — requiring **8 of 10** cycles where a buffer filled
with `-1.0f` returns `kTestEchoConstant` at channel-0 first, channel-1 first, and channel-0 last
sample. Observed: 5-7 of 10, reliably across three runs.

The shape matters: this asserts a **success rate**, not correctness. A partial pass means most
round-trips work and a minority miss their deadline — the signature of the host's bounded spin-wait
plus `sem_timedwait` giving up and emitting the un-echoed buffer, not of a protocol or data-integrity
defect. Three hypotheses, probed in this order:

1. **Environmental / timing** — the worker misses the per-block deadline under load. Run the suite
   alone on an idle machine ×10; instrument the wait path to log actual round-trip latency against
   the timeout budget. Cheapest, and its result splits the tree.
2. **Merge regression** — check out the pre-merge parent, build in a scratch tree, run the same
   suite. The trace explicitly lacked this baseline; producing it is the discriminating experiment.
3. **Real IPC defect** — build with ThreadSanitizer and run. ASan precedent exists (two UAFs, 06-12).

**Do not** lower `requiredSuccesses` to make it pass — that converts a real signal into a silent one.

**T4-probe — The two R4 suspects, sequenced FIRST**

These two determine the shape of everything else in class C:

- **`RingBufferTests`** — expects capacity 256, gets 255. An off-by-one that is equally consistent
  with a genuine `RingBuffer` bug as with a bad test.
- **`RerouteNodeTests`** — expects `AudioRerouteNode` to report 0 MIDI ports; it reports 1. Which is
  correct is a *design* question, not a test question.

For each: read the quarantine claim, read the implementation, and decide **who is wrong** before
touching either.

**RE-DECISION POINT.** Report both outcomes, then choose the remaining shape:

- **Both are genuinely bad tests** → the "test-side error" label is trustworthy; the remaining 13
  class-C suites are mechanical, and the remaining work can run as parallel lanes (tests · UI), with
  the plugin build already de-risked in P1.5b.
- **Either is a real engine bug** → the label is not trustworthy; class C becomes an
  engine-debugging effort. Re-scope, re-resource, and re-sequence before proceeding, and re-examine
  whether "all suites green" is still the right ship bar.

## 8. Architecture Decision Records

### ADR-1 — Sequence as serial de-risking followed by an evidence-shaped fork (Option B-prime)

**Decision.** Do not commit to a lane structure up front. Run P0 → P1 → P1.5b → P2a, then re-decide
the remaining shape against evidence from P2a.

**Drivers.** (a) Two unknowns materially change the plan's shape and both are cheap to resolve: the
plugin build has never been configured (F8) and the "test-side error" label is unverified (F3/R4).
(b) The F11 helper defect guarantees the critical-path test fails today, so it must be fixed before
anything downstream is meaningful. (c) Revision 1's parallel Lane P had a self-contradicting
acceptance criterion.

**Alternatives.** *Option A (sequential)* — reaches the two riskiest items last. *Option B
(three-lane parallel)* — Lane P's `dist`-freshness gate is falsified by Lane U's commits; viable only
with an explicit commit pin plus P3 re-verification. *Option C (ship-gate-minimal)* — fastest, but
overrules two of Glen's locked answers.

**Why this one.** The two de-risking items (P1.5b, P2a) are both **S**, both serial, and both
collapse a large uncertainty. Doing them first costs little and can save re-planning an entire lane.
Crucially, P1.5b removes the need for a parallel plugin lane at all, which dissolves Option B's
contradiction rather than patching it.

**Consequences.** The total shape is not knowable at approval time — honest, but harder to schedule.
One explicit decision point must be honoured rather than skipped under time pressure. Parallelism
starts later, but on firmer ground.

**Follow-ups.** Record P2a's outcome and the resulting shape in the closeout note. If P2a finds a
real engine bug, re-run this ADR's reasoning before committing to lanes.

### ADR-2 — Account for all 28 suites as 27 green plus 1 documented feature gate

**Decision.** Keep `SandboxCVTransportTests` registered DISABLED with its existing rationale and a
backlog pointer. Report the bar as "28/28 accounted for", not "27/28".

**Drivers.** (a) It is a failing-by-design gate, self-documented as such at
`test/CMakeLists.txt:361-364`. (b) Making it green means an RT-critical shared-memory ABI change.
(c) No ship gate, verdict, or deliverable depends on CV reaching a sandboxed plugin.

**Alternatives.** *Build it* — correct eventually, but an L engine feature smuggled into a test
phase. *Delete the registration* — destroys the gap marker's value as a tracked reminder.

**Why this one.** The suite's purpose is to *mark* a known gap, and it currently does that job
correctly. Deleting it loses information; building it now buys nothing the ship needs. The framing
matters: "27/28" implies unfinished cleanup, while "28/28 accounted for, one deliberate gate" states
the actual engineering position.

**Consequences.** Departs from the spec's literal wording, so it needs Glen's sign-off (P0.7). The
CV gap persists and must appear in the release note.

**Follow-ups.** Backlog `.omo/plans/sandbox-cv-transport-design-2026-06-06.md` as post-ship; note it
in P6.6.

### ADR-3 — Drop `gui-vs-features` rather than port it

**Decision.** Tag `archive/gui-vs-features-superseded`, optionally cherry-pick `ConsolePanel.tsx`,
delete the branch, and let PRs #1 and #2 close.

**Drivers.** (a) 19 merge-tree conflicts including 4 add/add, over 302 commits of wave-3 drift.
(b) The headline deliverable is superseded 999-vs-596 lines with stories and tests the branch lacks.
(c) Two of its files target D3-shelved UI. (d) Only one file is genuinely unique.

**Alternatives.** *Port it* — spec AC-1's literal reading; means hand-resolving 19 conflicts to
import work that is worse than what exists. *Leave the branch and PRs open* — carries a permanently
stale branch and two misleading open PRs.

**Why this one.** Porting has negative expected value: the cost is high, the risk of regressing
better code is real, and the recovered value is one file that can be taken directly. Tagging rather
than deleting outright preserves the history at zero cost.

**Consequences.** Contradicts spec AC-1's wording — needs Glen's sign-off (P0.8). Two PRs close
automatically; `local-enhancements` needs a disposition because it is PR #1's base.

**Follow-ups.** Record the tag SHA and each PR's final state in the closeout note.
