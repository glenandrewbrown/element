Option 2 — Count Badges + IO Summary · Design Rationale
What it shows
Three compact zones replace the thumbnail: (1) category composition chips — one chip per category present, with a count and the canonical ●▲◆⬡ glyph; (2) a signal IO summary bar showing input/output signal types and counts; (3) an action row with Enter (primary) and Edit. The block stays close to normal block height (+40–50px at most).
Implementation cost
Low. All data is already available: containerNodeCount exists on BlockData. A category breakdown (how many of each type) needs one extra host field or is derived client-side from the container's block list in the graph store. No SVG generation, no snapshot logic. The compact tier (dots + IO) just reads the same data.
Trade-offs
Pro: same compact footprint as a normal block (+2 zones). No implementation risk. Portal/Container/nested containers all work identically — just different badge text. Works at all zoom levels (compact tier at low zoom is just dots). Con: no spatial memory — two containers with the same category mix look identical. The user must remember names, not shapes.
Option 1 (Thumbnail) strengths
Spatial identity — topology shape is visually unique per container
Communicates graph complexity at a glance
+96px height — bigger footprint on canvas
Moderate implementation cost (SVG snapshot generation)
Thumbnail becomes misleading after internal edits until regenerated
Option 2 (Badges) strengths
Near-zero implementation cost — all data already available
Compact — close to normal block height
Always accurate — live counts, no snapshot staleness
No spatial identity — two "2 FX + 1 VI" containers look identical
Does not communicate internal wiring topology
