## A. Sandbox explainer (present this to Glen first thing)

The "sandbox" feature in Element is **out-of-process plugin hosting**. Plain English:

- Normally when you load a plugin in Element (a synth, a compressor, an EQ), the plugin's code runs **inside Element's own process**. If the plugin has a bug and crashes, it crashes Element with it. You lose your unsaved work.
- The **sandbox** runs each plugin in a **separate process**. Element talks to it through shared memory (audio buffers + parameter messages). If the plugin crashes, only the sandbox process dies. Element survives, can restart it, and your session keeps going.
- This is the same thing browsers do for tabs, and the same thing pro-tier hosts (REAPER, Pro Tools, Bitwig) offer.

**Why does it matter for Element specifically?**
- Some commercial plugins are notoriously crashy. iZotope, Waves, FabFilter occasionally produce bad versions; iLok-protected plugins fail dramatically.
- Without sandboxing, Element will get blamed when a third-party plugin causes a crash.
- A working sandbox is a **competitive feature** — it's table stakes for "professional plugin host".

**What's broken right now?**
The forensic audit (March 30) declared *"the out-of-process plugin sandbox has never functioned correctly"*. Six co-dependent issues:

1. The signaling between processes uses semaphores that are **process-local** — they can't actually wake the other side.
2. Atomic operations in the shared memory are **undefined behaviour** (C++20 `std::atomic` isn't safe across process boundaries — needs `std::atomic_ref`).
3. Both sides re-initialise the shared header, **zeroing the sequence counters**.
4. Host **frees the shared memory before the worker stops using it**.
5. After a plugin crash, recovery hangs because `waitForResponse` doesn't unblock.
6. Restart sequence sends "load this state" **before** the new plugin has loaded.

All six must be fixed together — they're co-dependent. Hence the **2-week** estimate.

**Three options for Glen:**

| Option | What it means | Cost |
|---|---|---|
| **A. Full redesign (Phase D in scope)** | Fix all 6 issues, sandbox works for real. Adds Wave 2 (~2 weeks). | +2 weeks; +1 milestone gate |
| **B. Feature-flag and ship without it** | Add `ELEMENT_ENABLE_SANDBOX=OFF` default + UI label "experimental: not recommended" + docs note. Defer redesign to a future cycle. | ~2 hours total; no other impact |
| **C. Keep as-is (currently broken-by-default)** | Don't touch it; risk: someone enables it in settings and corrupts a session | not recommended |

**My recommendation:** **Option B (feature-flag)** unless sandboxing is a key marketing point for Element 1.0. The 6-week-to-3-week wall-clock saving is significant and the redesign can land in a 1.1 update.
